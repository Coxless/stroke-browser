1. 全体の層

Stroke は、上から順に次の層でできています。ポイントは、キーを最初に受け取るのは常に外枠（crates/stroke）だということと、外枠は Servo の型に直接触らないことです。外枠とエンジンの間には Engine trait という薄い境界があります。

OS・表示サーバー（Wayland）
ウィンドウ、キー、IME、GPU
winit
ウィンドウを作り、OS のイベントを WindowEvent として届けるイベントループ
外枠 — crates/stroke
キーの振り分け、URL 入力欄と状態表示、全体の配線
main.rs（App / Running） shortcuts.rs（仮のキー） location.rs（入力 → URL） ui.rs（egui）
↓ 操作（load, send_key …）↑ 通知（EngineEvent）
Engine trait — crates/stroke-engine/src/lib.rs
ここより上に Servo の型は出さない（winit と glow の型は出してよい）
エンジン層 — crates/stroke-engine
Engine の Servo 実装と、通知の受け取り、読み込みの規則
servo_engine.rs（ServoEngine / Delegate） keys.rs（キーの変換） policy.rs（開いてよい URL）
Servo 0.1.4（crates.io の LTS 版）
HTML・CSS の解析、レイアウト、描画、ネットワーク。赤枠は vendor/ で手を入れた crate
constellation script（JS を止めた） layout / style net（リダイレクト先を渡す） WebRender SpiderMonkey

この作りは、Servo のお手本の外枠である servoshell と同じです（docs/decisions.md の「外枠の UI は winit ＋ egui で作る」）。困ったときは servoshell のソースが読めます。

3. 外枠とエンジンの境界（Engine trait）

crates/stroke-engine/src/lib.rs:69 の Engine trait が、外枠から見たエンジンのすべてです。メソッドは役割ごとに4つに分かれています。

グループメソッド向き
外枠からの操作load go_back go_forward reload send_key send_ime evaluate_script外枠 → エンジン
今の状態url title load_state can_go_back can_go_forward外枠が聞きに行く
エンジンからの通知spin take_eventsエンジン → 外枠（外枠が取りに行く）
表示gl make_current resize_window resize_view paint composite_fn begin_frame presentOpenGL の文脈を共有して描く

通知は「溜めて、取りに行く」

Servo は、ページの URL やタイトルが変わったり、新しい画面が描けたりすると、WebViewDelegate のメソッド（notify_url_changed など）を呼びます。Stroke ではこれを Delegate（servo_engine.rs:203）が受け取り、EngineEvent に直して Vec に溜めるだけにしています。外枠は spin() の後に take_events() でまとめて取り出して処理します（main.rs:152）。

こうすると、外枠の状態（ウィンドウ、UI）を触るのは外枠のコードだけになり、Servo の呼び出しの途中で外枠の状態を書き換える、ということが起きません。

EngineEvent外枠がすること（main.rs の Running::spin）
NewFrameReady、LoadStateChangedウィンドウの描き直しを頼む
UrlChanged止めたというお知らせを消し、描き直す
TitleChangedウィンドウのタイトルを「〇〇 — Stroke」にする
InputMethodShown / HiddenIME を有効・無効にし、変換候補の位置を入力欄に合わせる
RequestBlocked画面下に「開かなかった（理由）」を出す

4. イベントループと「起こす」仕組み

Stroke のメインスレッドは、winit のイベントループ1本だけです。winit は、何かイベントが来るまで眠っています。ところが Servo は、ネットワークやレイアウトの仕事を別のスレッドで進めます。別のスレッドで仕事が終わったとき、眠っているメインスレッドを起こす必要があります。

  1. Servo の別スレッドで、ページの読み込みや描画が進む
  2. Servo が EventLoopWaker::wake() を呼ぶ。Stroke の Waker は、起動時に外枠から渡された関数を呼ぶだけ servo_engine.rs:357 Waker
  3. その関数は proxy.send_event(AppEvent::Wake) で、winit のイベントループにユーザーイベントを投げる main.rs:96–103
  4. winit が目を覚まし、App::user_event が呼ばれる → Running::spin() main.rs:123
  5. engine.spin() が servo.spin_event_loop() を呼ぶ。ここで Servo がメインスレッドでの仕事を進め、delegate のメソッドを呼ぶ → EngineEvent が溜まる servo_engine.rs:147
  6. take_events() で取り出して処理する main.rs:154

ウィンドウのイベント（キー、大きさの変化など）が来たときも、処理の前に必ず spin() を呼んでいます（main.rs:137）。AppEvent にはもう1つ Repaint があり、こちらは egui が「描き直したい」ときに使います（カーソルを動かしたときなど）。

winit の resumed（main.rs:84）は「ウィンドウを作ってよくなった」合図です。ウィンドウ、エンジン、UI はすべてここで作り、Running にまとめます。Running のフィールドの順番には意味があり、Rust は書いた順に片付けるので、egui の OpenGL の資源を、エンジンの OpenGL の文脈より先に片付けられるようにしています（main.rs:70–81）。

5. 流れ1：URL を開いてから画面に出るまで

外枠エンジン層Servo の中

URL 入力欄で打つ

  1. Ctrl+L を押す。キーは外枠が先に受け取り、shortcuts::command_for が Command::OpenLocation を返す main.rs:210–219、shortcuts.rs:19
  2. ui.open_location(今の URL) で入力欄を開く。この間、キーはページではなく egui に渡る main.rs:244、ui.rs:82
  3. Enter を押すと、egui が UiAction::Go(入力した文字) を返す ui.rs:185 location_bar
  4. location::resolve が文字を URL に直す。servo.org → https://servo.org/、手元以外の http: → https:、URL でなければ DuckDuckGo の検索の URL、file: などは断る location.rs:41
  5. engine.load(url) → webview.load(url) main.rs:280、servo_engine.rs:81

Servo が読み込んで描く

  1. Servo のネットワーク（net）が読み込みを始める前に、外枠に「読み込んでいいか」を聞く
  2. Delegate::load_web_resource → enforce_policy → policy::check。規則に合えば何もしない（Servo がそのまま読む）。合わなければ止める servo_engine.rs:232、301、policy.rs:34
  3. HTML を受け取り、script の中の HTML パーサーが DOM の木を作る。Stroke では、ここで文書に「スクリプトを動かさない」印を付けている（vendor/servo-script）
  4. CSS を解析してスタイルを決め、layout が箱の位置と大きさを決め、描くもの（ディスプレイリスト）を作る
  5. 途中で URL、タイトル、読み込みの状態が変わるたびに delegate を呼ぶ → UrlChanged、TitleChanged、LoadStateChanged が溜まる servo_engine.rs:242–257
  6. 新しい画面の準備ができると notify_new_frame_ready → NewFrameReady servo_engine.rs:259

外枠がウィンドウに出す

  1. NewFrameReady を受けて window.request_redraw()。winit から RedrawRequested が来る main.rs:159、200
  2. Running::redraw：ui.run が状態表示と URL 入力欄を組み立て、残りの領域をページの表示領域（view_rect）にする main.rs:267、ui.rs:92
  3. resize_view で表示領域に合わせ、paint() で WebRender にページを画面外のバッファへ描かせる ui.rs:119–124
  4. 画面外のバッファをウィンドウに写す関数（composite_fn）を、egui の一番下の層に登録する ui.rs:125–141
  5. begin_frame → ui.paint（まずページを写し、その上に egui の UI を描く）→ present でウィンドウに出す main.rs:270–272

6. 流れ2：キーを押してからページに届くまで

Stroke の主題は「キーボードだけで使い切る」ことです。そのために、キーは必ず外枠が先に受け取り、ページに渡すかを外枠が決めます。ふつうのブラウザの拡張機能ではページにキーを奪われることがありますが、外枠を自分で持てばそれが起きません。

  1. OS → winit → WindowEvent::KeyboardInput。修飾キーの状態は ModifiersChanged で別に届くので、Running.modifiers に覚えておく main.rs:204
  2. URL 入力欄が開いていれば、キーは egui に渡す（ページには届かない） main.rs:210 の if !self.ui.location_open()
  3. 開いていなければ、shortcuts::command_for で外枠の命令かを調べる。命令なら実行して終わり（ページには届かない） main.rs:211–219
  4. 命令でなければ engine.send_key(key, modifiers) main.rs:227
  5. keys::keyboard_event が winit のキーを W3C の KeyboardEvent の形（key、code、location、修飾キー）に直す keys.rs:14
  6. webview.notify_input_event(InputEvent::Keyboard(…)) で Servo に渡す servo_engine.rs:101
  7. Servo がフォーカスのある要素に keydown などを配る。ページの JS は止めてあるので、矢印や Space によるスクロールなど、ブラウザの既定の動作が起きる

キーの key と code

W3C のキーイベントには、key（論理的な意味。"a"、"Enter"）と code（物理的な位置。"KeyA"）の2つがあります。winit の logical_key と physical_key がそれぞれに当たります。winit の名前と W3C の名前はほとんど同じなので、keys.rs は名前の文字列を介して変換し、違うもの（Space は名前のキーではなく文字 " "、Super は Meta）だけ個別に直しています。

日本語入力（IME）の経路

IME はキーとは別の道を通ります。

  1. ページの入力欄にフォーカスが入ると、Servo が show_embedder_control(InputMethod) を呼ぶ
  2. Delegate が入力欄の位置を付けて InputMethodShown { area } を溜める servo_engine.rs:263
  3. 外枠が window.set_ime_allowed(true) と set_ime_cursor_area を呼ぶ。位置は「ページの表示領域の左上」＋「入力欄の位置」で、変換候補が入力欄のそばに出る main.rs:296 apply_page_ime
  4. IME から WindowEvent::Ime（変換中の文字 Preedit、確定 Commit）が来る → engine.send_ime main.rs:230
  5. W3C の composition イベント（Start / Update / End）に直して Servo に渡す servo_engine.rs:106

詳しくは docs/ime.md にあります。

7. 描画の重ね方

ウィンドウには、Servo が描いたページと、egui が描く外枠の UI の2つが出ます。この2つは同じ OpenGL の文脈を共有しています。

egui：URL 入力欄（開いているときだけ）
Servo が画面外のバッファに描いたページ
egui の一番下の層（LayerId::background()）に写す
egui：状態表示（読み込みの状態、お知らせ、URL、キーの一覧）
もの役割
WindowRenderingContextウィンドウそのものに描く OpenGL の文脈。最後に present でウィンドウに出す
OffscreenRenderingContextページを描く画面外のバッファ。大きさはページの表示領域に合わせる
composite_fn画面外のバッファを、ウィンドウの指定した長方形に写す関数。egui の PaintCallback の中で呼ばれる

座標系に気をつける

UI とエンジンの PixelRect は、原点がウィンドウの左上です。ところが OpenGL は原点が左下です。そのため composite_fn に渡す長方形だけは、egui の clip.from_bottom_px（下からの距離）を使っています（ui.rs:130–138）。

順番に気をつける

ui.run の中では、必ず「表示領域の大きさを変える → ページを描く → 写す関数を登録する」の順にしています。大きさを変えるとバッファが作り直されるので、逆にすると、写す関数が消されたバッファを指してしまいます（ui.rs:116–118 のコメント）。

8. 安全のための仕組み

Stroke は作りかけで、Servo もまだ若いエンジンです。そのため、攻撃を受ける面そのものを小さくする方針をとっています。

仕組みどこで何を防ぐか
ページの JS を動かさない vendor/servo-script（すべての文書にサンドボックスの印を付ける） ブラウザへの攻撃の多くは JS エンジン（JIT、WebAssembly、DOM との境目）を通る
開ける URL を絞る policy.rs の規則を3か所で使う（下の表） http: の書き換え、file: で手元のファイルを読まれること、data: の偽のページ
リダイレクト先も確かめる vendor/servo-net（外枠に今の URL を渡す） https: から http: へのリダイレクトですり抜けること
止めたページを無害にする enforce_policy が返す 403 のページに Content-Security-Policy: sandbox を付ける 止めた代わりのページが、どのオリジンの Cookie にも触れないようにする
閉じ込めて動かす workshop run -- run-browser（docs/dev-environment.md の「安全に動かす」） 乗っ取られても、ホームディレクトリや X11 の他の窓に届かないようにする

URL の規則を確かめる3か所

  1. URL 入力欄：location::resolve。http: を https: に直し、file: などは検索にも回さずに断る（打った文字が検索エンジンに漏れないように）
  2. ページからの移動（リンク、フォーム）：Delegate::request_navigation で断り、今のページに留まる servo_engine.rs:218
  3. すべての読み込み（ページ本体、画像などの資源、リダイレクト先）：load_web_resource → enforce_policy。資源は取り消し、ページ本体は「開かなかった」ページを代わりに返す servo_engine.rs:301
ページ本体の読み込みを取り消すと、Servo がそのページを待ったまま止まり、次の URL を開けなくなります。そのため、ページ本体だけは取り消さずに、代わりのページ（403）を返しています。

9. Servo の中（おおまか）

Stroke のコードが直接触るのは、主に Servo、WebView、delegate、描画の文脈だけですが、その奥では次のような部品が動いています。Phase 5 で中を読むときの地図にしてください。部品の分け方は版によって変わるので、読むときは Servo Book と Servo のソースで確かめます。

部品受け持ちStroke との関わり
constellationWebView とその中の文書（フレーム）を束ねる司令塔。移動や履歴を管理し、各部品の間でメッセージを中継するrequest_navigation などの問い合わせは、ここを経由して外枠に来る
scriptDOM、HTML パーサー、イベントの配送。JS は SpiderMonkey で動かすvendor/servo-script で JS を止めている。キーイベントもここで要素に配られる
style（Stylo）・layoutCSS からスタイルを決め、箱の位置と大きさを決めて、描くもののリストを作るPhase 5 でキャレットモードなどを作るときに読む
netHTTP、TLS、Cookie、キャッシュ。読み込みの前に外枠に問い合わせるload_web_resource はここから来る。vendor/servo-net で直した
WebRender描くもののリストを GPU で絵にするwebview.paint() で画面外のバッファに描かせている

Phase 0 のトイブラウザ（Web Browser Engineering）で作る「ダウンロード → 解析 → スタイル → レイアウト → 描画」の流れが、そのまま net → script → style・layout → WebRender に対応します。

11. 自分で確かめる

キーとエンジンの通知をログで見る

RUST_LOG=stroke=debug を付けると、押したキーの行き先と、エンジンからの通知がログに出ます。この資料の2つの流れが、実際にその順で起きることを確かめられます。

workshop shell
cd /project
RUST_LOG=stroke=debug,stroke_engine=debug env -u DISPLAY cargo run -p stroke -- servo.org

出てくるログの例（形を簡単にしたもの。実際の文言は main.rs と servo_engine.rs の log::debug! を見てください）：

キー CONTROL Character("l") → OpenLocation
開く https://example.com/
読み込み GET https://example.com/ (ページ本体: true, リダイレクト: false)
エンジン LoadStateChanged(Started)
エンジン UrlChanged(https://example.com/)
エンジン TitleChanged(Some("Example Domain"))
キー (empty) Named(ArrowDown) Pressed → ページ

単体テストを読む

規則とキーの変換は、ウィンドウがなくても確かめられるようにテストにしてあります。テストは「こう動くはず」の一覧として読めます。

cargo test
  • policy.rs のテスト：どの URL を許し、どれを止めるか
  • location.rs のテスト：打った文字がどの URL になるか
  • shortcuts.rs のテスト：どのキーが外枠の命令で、どれがページに行くか
  • keys.rs のテスト：winit のキーが W3C のどのキーになるか

やってみると理解が深まること

  • ☐ shortcuts.rs に新しい命令を1つ足し、main.rs の run_command で処理する（キーの経路の入口）
  • ☐ EngineEvent に1つ足し、Delegate で溜めて、外枠で状態表示に出す（通知の経路）
  • ☐ http://example.com/ を開こうとして、どこで止まるかをログで確かめる（安全の3か所）
  • ☐ servoshell の ports/servoshell/desktop/ を読み、Stroke と同じところ・違うところを探す
